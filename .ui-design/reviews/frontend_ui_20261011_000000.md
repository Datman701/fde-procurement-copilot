## Summary

The UI is unusually well-built for an assessment build: every state (loading, empty, error, result) is distinct and designed, the copy is honest about the copilot's boundaries, and the new "What we read from your request" panel is a genuinely good transparency pattern. The weaknesses are concentrated in **accessibility and CSS hygiene** rather than structure — there are **zero ARIA attributes, zero focus styles, and four measured WCAG AA contrast failures**, plus one real async race condition in the request-preview fetcher.

## Major Issues

### Issue 1: Stale request preview — async race in `useEffect`

**Severity:** Major
**Location:** `frontend/src/App.jsx:48-52`
**Category:** Code / Usability

**Problem:**

```jsx
useEffect(() => {
  if (!requestId) return;
  setRequestDetails(null);
  fetchRequestDetails(requestId).then(setRequestDetails).catch(() => setRequestDetails(null));
}, [requestId]);
```

Nothing cancels the in-flight request. Switch REQ-1001 → REQ-1002 quickly and the slower 1001 response can resolve *last*, overwriting the state so the panel shows REQ-1002's id in the `<select>` but REQ-1001's cost, vendor and justification in the summary box.

**Impact:** In a procurement tool the sidebar preview is what the user checks before pressing Run. Showing the wrong vendor or cost — even briefly, even though the analysis itself uses the correct id — is exactly the class of error this product exists to prevent.

**Recommendation:** Cancel on change and on unmount with `AbortController`, or at minimum guard with a stale-flag.

**Code Example:**

```jsx
// Before
useEffect(() => {
  if (!requestId) return;
  setRequestDetails(null);
  fetchRequestDetails(requestId).then(setRequestDetails).catch(() => setRequestDetails(null));
}, [requestId]);

// After
useEffect(() => {
  if (!requestId) return;
  const controller = new AbortController();
  setRequestDetails(null);
  fetchRequestDetails(requestId, controller.signal)
    .then(setRequestDetails)
    .catch(() => { if (!controller.signal.aborted) setRequestDetails(null); });
  return () => controller.abort();
}, [requestId]);
```

(`api.js` must forward the signal to `fetch`.)

### Issue 2: No focus styles anywhere in the stylesheet

**Severity:** Major
**Location:** `frontend/src/styles.css` (entire file)
**Category:** Usability / Accessibility

**Problem:** A scan for `:focus`, `:focus-visible` and `outline` returns **no matches**. Every interactive control — the segmented toggle, both selects, the textarea, the architecture radios, the checkboxes, the primary button, the three handoff buttons, and every `<summary>` — falls back to the browser's default ring.

That default is actively poor here: `.segmented button` has `border: none` and `background: transparent` on a `#e8edf6` track, and `.arch-card input` is a bare radio inside a padded label. A keyboard user tabbing through the form gets inconsistent, sometimes nearly invisible indication of where they are.

**Impact:** Keyboard-only operation is a primary path for a data-entry tool. Inconsistent focus is the single most common reason a keyboard user loses their place.

**Recommendation:** Add one global, deliberate focus treatment using the existing accent token, and apply `:focus-visible` so mouse users don't see it.

**Code Example:**

```css
/* After — append to styles.css */
:where(a, button, input, select, textarea, summary):focus-visible {
  outline: 2px solid var(--accent);
  outline-offset: 2px;
  border-radius: 4px;
}
```

### Issue 3: Zero ARIA — results and errors are never announced

**Severity:** Major
**Location:** `frontend/src/App.jsx`, `frontend/src/components.jsx`
**Category:** Accessibility

**Problem:** A scan for `aria-*` and `role=` across both JSX files returns **zero matches**. The three `htmlFor` attributes in `App.jsx` are the only accessibility affordances in the entire UI. Three concrete gaps:

1. **Errors are silent.** `<div className="banner error">` at `App.jsx:251` and `:329` has no `role="alert"`. A screen-reader user who presses *Run analysis* and gets a 503 gets no announcement at all.
2. **Results are silent.** Analysis takes 10–40 seconds. When it finishes, the DOM below is replaced with a verdict banner and six panels, and nothing is announced. The user has no way to know the run completed without re-reading the page.
3. **The segmented control is unlabelled.** Two `<button>`s act as a single toggle; assistive tech announces two unrelated buttons with no indication of which is selected.

**Impact:** These are the three highest-traffic dynamic events in the app, and all three are invisible to assistive technology.

**Recommendation:**

```jsx
// Errors
<div className="banner error" role="alert">⚠️ {error}</div>

// Results container
<main className="results" aria-live="polite" aria-busy={loading}>

// Segmented control
<div className="segmented" role="group" aria-label="Request source">
  <button aria-pressed={source === "catalog"} onClick={() => setSource("catalog")}>
    Pick a request
  </button>
  <button aria-pressed={source === "free_text"} onClick={() => setSource("free_text")}>
    Describe it in words
  </button>
</div>
```

### Issue 4: Four measured WCAG AA contrast failures

**Severity:** Major
**Location:** `frontend/src/styles.css:326-327,347,363-368`
**Category:** Visual / Accessibility

**Problem:** Measured against WCAG 2.2 SC 1.4.3 (AA requires 4.5:1 for normal text). These are not estimates — they are computed from the declared hex values:

| Selector | Foreground / Background | Size | Ratio | AA |
|---|---|---|---|---|
| `.badge.conflict` | `#d99a26` / `#fdf3e0` | 11px | **2.22:1** | **FAIL** (also fails large-text 3:1) |
| `.badge.failed` | `#d64545` / `#fdeaea` | 11px | **3.78:1** | **FAIL** |
| `.error-text` | `#d64545` / `#ffffff` | 13px | **4.38:1** | **FAIL** |
| `.handoff-row button.danger` | `#ffffff` / `#d64545` | 13.5px | **4.38:1** | **FAIL** |

For reference, `--amber-line: #d99a26` is a *border* token being reused as text colour. Borders need 3:1; text needs 4.5:1. The palette conflates the two roles.

**Impact:** `CONFLICT` and `FAILED` badges mark exactly the tool results the user must not miss. At 11px and 2.22:1 the CONFLICT badge is unreadable for a large fraction of users — including anyone with low vision, and including anyone glancing at a projector in a review.

**Recommendation:** Introduce separate `-text` tokens alongside the existing border tokens, and darken the red used on white.

```css
:root {
  /* borders (need 3:1) — unchanged */
  --amber-line: #d99a26;
  --red-line:   #d64545;
  /* text on tinted/white backgrounds (need 4.5:1) — new */
  --amber-ink:  #8a5a00;  /* 5.4:1 on #fdf3e0 */
  --red-ink:    #b3261e;  /* 5.9:1 on #ffffff, 5.1:1 on #fdeaea */
}

.badge.failed   { background: var(--red-bg);   color: var(--red-ink); }
.badge.conflict { background: var(--amber-bg); color: var(--amber-ink); }
.error-text     { color: var(--red-ink); }
.handoff-row button.danger {
  background: var(--red-ink);
  border-color: var(--red-ink);
  color: #fff; /* 5.9:1 */
}
```

### Issue 5: No request timeout or cancel — a hung call is an infinite spinner

**Severity:** Major
**Location:** `frontend/src/api.js:3-16`, `frontend/src/App.jsx:57-78`
**Category:** Usability / Code

**Problem:** `runAnalysis` has no timeout and no `AbortController`. `loading` is only cleared in `finally`, so a request that never resolves leaves the spinner spinning forever with no way out except reloading the page. The UI already tells the user to expect "10–40 seconds", which sets an expectation the code does not enforce.

**Impact:** The analysis path hits a live LLM. A provider stall is not a hypothetical — the project's own eval records a 503 mid-run (EVAL-23). The user's only recovery today is a hard reload.

**Recommendation:** Add a timeout (the UI already quotes 40s; use ~90s for headroom) and wire `AbortController` through `runAnalysis`, plus an explicit *Cancel* button shown while loading.

```jsx
async function analyze() {
  const controller = new AbortController();
  const timer = setTimeout(() => controller.abort(), 90_000);
  setLoading(true);
  try {
    const data = await runAnalysis(payload, controller.signal);
    setResult(data);
  } catch (err) {
    setError(controller.signal.aborted
      ? "Analysis timed out after 90 seconds. Try again, or enable the response cache."
      : err.message);
  } finally {
    clearTimeout(timer);
    setLoading(false);
  }
}
```

### Issue 6: Disabled handoff buttons give no reason

**Severity:** Major
**Location:** `frontend/src/App.jsx:359-383`
**Category:** Usability

**Problem:** Three handoff buttons are conditionally disabled (`App.jsx:361, 369, 378`). "Escalate to security" is greyed at `opacity: 0.45` whenever severity isn't `ESCALATE_TO_HUMAN`, and "Request info from employee" is greyed whenever nothing is missing — but nothing on screen says *why*. A disabled control with no explanation reads as a broken control.

This is especially confusing on this button, because the escalate path is the one users most want to try.

**Impact:** Disabled-without-why is one of the most common causes of "is this broken?" in usability testing. Here it also hides a deliberate design decision (escalation is rule-driven, not user-driven).

**Recommendation:** Keep the buttons enabled-looking but explain the precondition in-place, or add an inline `title`/helper line. Simplest fix that preserves the current semantics:

```jsx
<button
  className={decision.severity === "ESCALATE_TO_HUMAN" ? "danger" : ""}
  disabled={decision.severity !== "ESCALATE_TO_HUMAN"}
  title={decision.severity !== "ESCALATE_TO_HUMAN"
    ? "Only available when the verdict is Escalate to a human"
    : undefined}
>
  Escalate to security
</button>
```

Better still: render the reason as visible text rather than a tooltip, since tooltips are not reachable on touch or by screen reader reliably.

## Minor Issues

### Issue 7: No type or spacing scale — 11 font sizes and 9 radii

**Severity:** Minor
**Location:** `frontend/src/styles.css`
**Category:** Visual / Code

**Problem:** The stylesheet defines `:root` tokens for colour and a single `--radius`, then largely ignores them. Font sizes used: 11, 11.5, 12, 12.5, 13, 13.5, 14.5, 16, 17, 20, 26px. Border radii: 4, 5, 6, 8, 10, 999px — and `--radius: 10px` is applied to only two selectors (`.panel`, `.verdict`) while everything else hardcodes 8px.

**Impact:** Not a visual bug today — the values were chosen carefully. But any future change (e.g. bumping body text) requires a manual sweep of ~20 declarations, which is how drift starts.

**Recommendation:** Promote the existing values to tokens. Low-risk, purely mechanical.

```css
:root {
  --fs-xs: 11.5px;  --fs-sm: 12.5px;  --fs-base: 15px;
  --fs-md: 13.5px;  --fs-lg: 17px;    --fs-xl: 20px;
  --sp-1: 4px; --sp-2: 8px; --sp-3: 12px; --sp-4: 16px; --sp-5: 22px;
  --radius: 8px; --radius-lg: 10px; --radius-pill: 999px;
}
```

### Issue 8: No `prefers-reduced-motion`

**Severity:** Minor
**Location:** `frontend/src/styles.css:236`
**Category:** Accessibility

**Problem:** The loading spinner runs `animation: spin 0.9s linear infinite` with no reduced-motion guard.

**Impact:** Vestibular disorders make continuous rotation genuinely unpleasant. This spinner runs for 10–40 seconds at a time, which is a long exposure.

**Recommendation:**

```css
@media (prefers-reduced-motion: reduce) {
  .spinner { animation-duration: 2.5s; }
}
```

(Slowing rather than removing keeps the "still working" signal intact.)

### Issue 9: Emoji as the sole severity marker, with no `aria-hidden`

**Severity:** Minor
**Location:** `frontend/src/components.jsx:7,13,19,92-97`
**Category:** Accessibility / Visual

**Problem:** `✅ ⚠️ 🚨 🔴 🟠 🔵 ⚪` carry meaning. Screen readers announce their names ("white heavy check mark", "triangular flag"), which adds noise on top of the adjacent text labels. They are also the *only* shape distinguishing risk-flag severities — the colour is the other cue, which fails for colour-blind users.

**Impact:** Mild. The text labels (`Within policy — proceed`, the flag `<code>`) do carry the meaning, so nothing is truly lost. The issue is announcement noise and reliance on colour for the flag severity.

**Recommendation:** Mark decorative emoji `aria-hidden="true"` and pair each flag colour with a text severity label.

```jsx
<span className="verdict-icon" aria-hidden="true">{s.icon}</span>
```

### Issue 12: Catalog load failure is permanent and unrecoverable

**Severity:** Minor
**Location:** `frontend/src/App.jsx:39-46`
**Category:** Usability

**Problem:** If `fetchCatalog()` rejects, the error is set — but there is no retry affordance, and the `<select>` renders empty. The only recovery is a full page reload. Note also that `analyze()` calls `setError(null)`, so pressing *Run analysis* clears the catalog error while leaving the dropdown still empty.

**Impact:** The catalog is a local endpoint that essentially cannot fail in this deployment. Low practical risk; flagged because the pattern is fragile.

**Recommendation:** A small retry button in the error banner, and don't let `analyze()` clear a load-time error it can't fix.

## Suggestions

### Suggestion 1: Bundle size is fine — don't code-split yet

`index-Cu08KOHe.js` is 158 KB raw (~46 KB gzip), of which React + ReactDOM is the bulk. There is one route and no heavy dependency. Splitting would add a loading state for no benefit. Revisit only if a chart or PDF library is added.

### Suggestion 2: Copy button on "Raw decision JSON"

`components.jsx:213` dumps the full decision into a `<pre>`. A copy-to-clipboard button makes this far more useful for pasting into a ticket, which is the obvious next action.

### Suggestion 3: Keyboard shortcut for Run

A data-entry tool with one primary action benefits from `Cmd/Ctrl+Enter` to submit from the textarea. Pairs well with leaving Enter free for newlines.

### Suggestion 4: `prefers-color-scheme` dark theme

The palette is tokenised in `:root` already, so a `@media (prefers-color-scheme: dark)` block overriding ~10 tokens is cheap. Out of scope for an assessment build — noted as the natural next step.

### Suggestion 5: `meta name="description"` and `theme-color`

`index.html` has `lang` and `viewport` (good) but no description or theme colour. Cosmetic; matters only if the URL is ever shared.

### Suggestion 6: `toolNameOf` runs inside `.map()`

`App.jsx:346` calls `toolNameOf(e.result_id, toolResults)` per evidence card — O(n·m). Both are ≤6 items, so this is not measurable. Noted only so it isn't copied into a larger list.

## Positive Observations

- **Every state is designed.** Loading, empty, error, and result are four distinct, considered layouts — not a blank div. The empty state explains the workflow; the loading state names the four evidence sources and quotes a duration.
- **The copy sets honest boundaries.** "Evidence-gathering and recommendation only. It cannot approve spend, purchase software, change a budget, or override Security / Privacy / Legal" in the header, reinforced in the footer and the handoff disclaimer. Consistent and unmissable.
- **The ExtractionPanel is the best pattern in the UI.** Showing each recovered field *with the exact wording that justified it* is a high-quality transparency affordance, and it directly supports the product's "nothing is guessed" claim.
- **Colour tokens are genuinely used.** The core palette (`--ink`, `--muted`, `--line`, `--accent`, the three semantic pairs) is referenced consistently rather than re-hardcoded. The contrast failures above come from *border* tokens being reused as text, not from a missing token system.
- **`details`/`summary` for progressive disclosure** is used correctly throughout — tool results, guardrail notes, reviewer tightening, raw JSON. Keeps the default view scannable while keeping everything reachable.
- **Form controls are properly labelled.** Every `<select>` and `<textarea>` has a matching `htmlFor`/`id` pair, and `index.html` correctly sets `lang="en"` and a viewport meta.
- **Numbered steps** (`1 · What is being requested?`, `2 · How should it be analysed?`) give the setup panel a clear reading order.
- **`api.js` is a clean thin wrapper** with proper `encodeURIComponent` and JSON error-detail extraction. Good boundary.
